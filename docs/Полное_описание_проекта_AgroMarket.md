# AgroMarket — полное описание проекта

**Версия документа:** 1.0  
**Дата анализа:** 22 июня 2026 года  
**Основание:** текущий код Android-приложения, развернутый OpenAPI-контракт `https://agro.assaru.space/openapi.json`, развернутая web-админка `https://agro.assaru.space/admin/`, проектная документация и handoff-файлы.

> Важно: локальный репозиторий содержит исходный код Android-клиента. Исходники backend и Vue-админки находятся на VPS и в этот git-репозиторий не входят. Поэтому клиентская механика описана по коду, админка — по фактически развернутому JavaScript и OpenAPI, а серверные меры защиты, которые нельзя проверить без исходников и конфигурации VPS, помечены как неподтвержденные.

## 1. Назначение проекта

AgroMarket — маркетплейс объявлений для аграрного сектора Российской Федерации. Основной пользовательский интерфейс — нативное Android-приложение. Пользователь регистрируется по email, просматривает каталог, сохраняет объявления, публикует собственные предложения, получает замечания модератора и повторно отправляет исправленное объявление.

Проект поддерживает три серверных типа объявлений:

- `sale` — продажа;
- `rent` — аренда;
- `service` — агроуслуги.

Земля не является отдельным серверным типом. В Android пункт «Земли СХ назначения» преобразуется в `type=sale` и категорию «Земельные участки» (`category_id=56`). Аренда присутствует в API и админке, но отдельного универсального пункта «Аренда» в текущем мастере Android нет.

Система состоит из следующих частей:

1. Android-клиент на Kotlin и Jetpack Compose.
2. REST API на FastAPI по адресу `https://agro.assaru.space/api/v1/`.
3. PostgreSQL в Supabase через Transaction Pooler.
4. Vue-админка по адресу `https://agro.assaru.space/admin/`.
5. Firebase Cloud Messaging для push-уведомлений.
6. DaData для загрузки районов и населенных пунктов с последующим кэшированием в БД.
7. Серверные платежные endpoints ЮKassa; полноценный платежный сценарий в Android пока не подключен.

## 2. Пользователи и роли

### 2.1. Неавторизованный посетитель

Неавторизованный пользователь не попадает в каталог. Ему доступны только:

- вход по email и паролю;
- трехшаговая регистрация: email → код из письма → установка пароля;
- восстановление пароля: email → код → новый пароль.

После получения JWT приложение сохраняет access- и refresh-токены и открывает каталог.

### 2.2. Зарегистрированный пользователь

Отдельных ролей «покупатель», «продавец», «арендодатель» или «исполнитель» нет. Один аккаунт одновременно может:

- искать товары и услуги;
- звонить по объявлению;
- создавать запрос на получение контактов;
- добавлять объявления в избранное;
- продавать товар;
- предлагать агроуслугу;
- размещать сельскохозяйственную землю;
- управлять своим профилем и своими объявлениями.

Практически пользователь переключается между ролями через действие: при просмотре он покупатель/заказчик, при размещении — продавец/исполнитель.

### 2.3. Владелец объявления

Владелец создает объявление, прикладывает фотографии, отправляет его на модерацию, отслеживает статус, удаляет объявление и исправляет его после возврата модератором.

В разделе «Мои объявления» видны заголовок, фото, статус и первая строка комментария модератора. Полный комментарий и фото-примеры показываются в карточке объявления.

### 2.4. Администратор

Администратор работает в отдельной web-панели. Он:

- видит статистику проекта;
- модерирует объявления;
- возвращает объявления на исправление;
- отклоняет или публикует объявления;
- прикладывает до пяти фото-примеров к замечанию;
- рассматривает запросы на контакты;
- назначает стоимость контактов, выдает их бесплатно или отклоняет запрос;
- просматривает и удаляет любые объявления;
- ищет, блокирует и разблокирует пользователей.

В API пользователь и администратор различаются флагом `is_admin`; отдельной расширенной модели ролей нет.

## 3. Полная пользовательская механика

### 3.1. Регистрация и вход

Регистрация проходит в три шага:

1. Пользователь вводит email; сервер отправляет проверочный код.
2. Пользователь вводит код; сервер его проверяет.
3. Пользователь задает пароль; сервер создает аккаунт и возвращает JWT.

Минимальная длина пароля в Android — 8 символов. Для входа используются email и пароль. При забытом пароле код отправляется на email. В профиле пароль можно сменить только с указанием текущего пароля.

При истечении access-токена Android автоматически использует refresh-токен. Если обновление не удалось, токены удаляются и пользователь возвращается на экран входа.

### 3.2. Каталог

Каталог — стартовый экран авторизованного пользователя. Карточка объявления показывает:

- главное фото;
- тип: продажа, аренда или услуга;
- отметку продвижения «В топе», если есть буст;
- цену;
- заголовок;
- субъект РФ/регион;
- кнопку избранного.

Лента загружается постранично по 20 объявлений. Следующая страница подгружается при достижении конца списка. Сервер сортирует продвигаемые объявления выше обычных: сначала `top_30days`, затем `top_7days`, после этого — по дате публикации.

### 3.3. Карточка объявления

Полная карточка содержит:

- фотогалерею со счетчиком;
- полноэкранный просмотр;
- свайп между фотографиями;
- масштабирование pinch-to-zoom и двойным нажатием;
- тип, заголовок и цену;
- регион, район и населенный пункт;
- путь категории «родитель → подкатегория»;
- описание;
- основной и дополнительный телефон;
- кнопки «Позвонить» и «Контакты»;
- добавление/удаление из избранного.

«Позвонить» открывает системный номеронабиратель через `ACTION_DIAL`; приложение само звонок не совершает и разрешение на прямой вызов не запрашивает.

Кнопка «Контакты» создает серверную заявку. Однако текущая карточка одновременно показывает телефон продавца всем авторизованным пользователям. Это противоречит механике платного доступа к контактам: контакт уже доступен до оплаты или одобрения заявки.

### 3.4. Избранное

Пользователь добавляет объявление сердечком в каталоге или карточке. Изменение выполняется оптимистично: интерфейс меняется сразу, а при ошибке сервера откатывается.

Во вкладке «Избранное» объявления можно удалить свайпом или кнопкой. После удаления доступна отмена через Snackbar. Неактивные объявления приглушаются и перемещаются вниз списка.

### 3.5. Профиль

Профиль содержит:

- аватар;
- фамилию и имя;
- email;
- телефон;
- регион, если он заполнен на сервере;
- смену пароля;
- список «Мои объявления»;
- выход из аккаунта.

Пользователь может изменить имя, фамилию, телефон и аватар. Поле региона отображается, но текущий экран редактирования профиля не дает выбрать новый регион.

### 3.6. Мои объявления

Для каждого объявления отображаются фото, название и статус. Доступно безвозвратное удаление после подтверждения. Нажатие открывает полную карточку.

Если объявление возвращено на доработку, владелец видит комментарий и фото модератора. Кнопка редактирования находится в полной карточке, а не в меню строки «Мои объявления».

## 4. Какие объявления можно размещать

### 4.1. Типы в мастере Android

Мастер предлагает три сценария:

1. «Продать» — зерно, техника, скот и другие товары.
2. «Агроуслуги» — обработка, перевозка, ремонт и другие работы.
3. «Земли СХ назначения» — продажа и аренда участков, но технически отправляется как `sale` в категории земли.

### 4.2. Категории

Реальное дерево категорий загружается с сервера. Пользователь сначала выбирает корневую категорию, затем обязательную подкатегорию, если у корневой категории есть дочерние элементы. В запрос отправляется реальный ID конечной категории.

На экране каталога есть статический ряд быстрых групп:

- Техника: тракторы, комбайны, сеялки, опрыскиватели, культиваторы;
- Запчасти: к тракторам, к комбайнам, фильтры, ремни;
- Семена: пшеница, подсолнечник, кукуруза, соя;
- Удобрения: азотные, фосфорные, калийные, комплексные;
- Корма: комбикорм, сено, силос, жмых;
- Животные: КРС, свиньи, птица, овцы;
- Земля: пашня, пастбища, аренда;
- Оборудование: доильное, зерносушилки, весовое;
- Прочее: инструменты, тара, стройматериалы.

Эти быстрые группы не являются серверным деревом категорий. Выбор подгруппы записывает ее название в строку поиска. Поэтому результат зависит от текстового поиска backend, а не от точного `category_id`.

### 4.3. Поля объявления

Обязательны:

- тип;
- конечная категория;
- субъект РФ/регион;
- название длиной не менее 5 символов;
- основной телефон;
- от 2 до 5 фотографий.

Необязательны:

- описание до 5000 символов по серверному контракту;
- цена;
- район;
- населенный пункт;
- дополнительный телефон — предусмотрен API, но отдельного поля в текущей Android-форме нет.

Телефон на сервере должен содержать 10–15 цифр и может начинаться с `+`. Цена не может быть отрицательной.

### 4.4. Черновик

Android автоматически сохраняет заполненные текстовые поля примерно через 800 мс после изменения. При следующем входе в мастер предлагает продолжить или начать заново.

Фотографии в локальный черновик не сохраняются, потому что временные URI Android могут перестать быть доступны после завершения процесса. После восстановления пользователь прикрепляет фото заново.

## 5. Создание, модерация и доработка объявления

### 5.1. Создание

Мастер состоит из 3–4 шагов:

1. Тип.
2. Корневая категория.
3. Подкатегория, если она есть.
4. Детали, география и фото.

Перед созданием Android локально проверяет обязательные поля и преобразует фотографии в файлы. Затем выполняется последовательность:

1. `POST /ads/` — создается серверный `draft`.
2. `POST /ads/{id}/photos` — загружаются 2–5 фото.
3. `POST /ads/{id}/submit` — объявление отправляется на модерацию.

Если фото не загрузились или отправка на модерацию завершилась ошибкой, новый серверный черновик удаляется, чтобы не оставлять осиротевшие записи.

Endpoint `submit` временно обходит оплату размещения. OpenAPI прямо указывает, что это временная схема до подключения ЮKassa.

### 5.2. Статусы

| Статус | Значение | Что видит пользователь |
|---|---|---|
| `draft` | Черновик на сервере | «Черновик» |
| `pending_payment` | Ожидается оплата | В Android нет отдельной русской метки |
| `pending_moderation` | Ожидает решения администратора | «На модерации» |
| `active` | Опубликовано | «Активно» |
| `needs_revision` | Возвращено владельцу | «На доработке» |
| `rejected` | Окончательно отклонено | «Отклонено» |
| `expired` | Срок публикации истек | В Android нет отдельной русской метки |
| `deleted` | Мягко удалено | В Android нет отдельной русской метки |

### 5.3. Действия модератора

В очереди модерации администратор видит категорию, географию, цену, телефоны, описание и все фото. Возможны три решения:

- «Опубликовать» (`approve`) — объявление становится активным;
- «На исправление» (`request_revision`) — обязателен комментарий, можно добавить до 5 фото-примеров;
- «Отклонить» (`reject`) — обязателен комментарий, также можно приложить до 5 фото.

Решение сохраняется первым. Фото загружаются вторым запросом. Если загрузка фото не удалась, решение уже остается примененным, а админка показывает предупреждение.

### 5.4. Доработка пользователем

Для `needs_revision` Android показывает:

- заголовок «Замечания модератора»;
- полный текст комментария;
- фото-примеры с полноэкранным просмотром;
- кнопку «Исправить и отправить снова».

Приложение загружает исходные поля и существующие фото. Пользователь может изменить данные, удалить существующие фото и добавить новые. После этого выполняются:

1. `PUT /ads/{id}`;
2. загрузка новых фото, если они есть;
3. `POST /ads/{id}/submit`.

Для `rejected` показывается причина отклонения без кнопки повторной отправки. В OpenAPI описание `PUT /ads/{id}` все еще говорит «только draft и rejected», тогда как клиент использует редактирование для `needs_revision`. Это несогласованность документации API, которую необходимо исправить.

### 5.5. Push-уведомления

Backend может уведомлять владельца об изменении статуса через FCM. Уведомление содержит `ad_id`; нажатие открывает нужную карточку. FCM-токен регистрируется после входа и при его обновлении. Если Firebase не инициализирован, логика работает как best-effort и не блокирует приложение.

### Нижняя навигация

1. **Каталог** — лента, поиск, фильтры, быстрые категории, переход в профиль.
2. **Избранное** — сохраненные объявления, свайп-удаление и отмена.
3. **Разместить** — мастер создания объявления.

### Дополнительные экраны

- Вход.
- Регистрация.
- Восстановление пароля.
- Полная карточка объявления.
- Редактирование объявления после модерации.
- Профиль.
- Смена пароля.

Отдельных вкладок «Мои заявки на контакты», «Оплаты», «Сообщения», «Уведомления» и «История модерации» в Android нет.

## 7. Фильтрация объявлений

### 7.1. Что работает в Android

В верхней части каталога постоянно видны чипы:

- «Все»;
- «Продажа» — `type=sale`;
- «Агроуслуги» — `type=service`;
- «Земли» — `category_id=56`.

Выбор типа сбрасывает категорию, выбор категории сбрасывает тип. Одновременно комбинировать тип и категорию текущий экран не умеет.

Текстовый поиск отправляется через 400 мс после прекращения ввода. Быстрая подкатегория также запускает текстовый поиск. Кнопка очистки сбрасывает текст и выбранную быструю группу.

### 7.2. Возможности backend

OpenAPI ленты поддерживает:

- страницу и размер страницы;
- тип;
- категорию;
- регион/субъект РФ;
- район;
- минимальную и максимальную цену;
- текстовый поиск.

### 7.3. Функциональный разрыв

Текущий Android-интерфейс не дает выбрать субъект РФ для фильтрации каталога. Хотя Retrofit-модель содержит `region_id`, `FeedViewModel` его не передает. `district_id`, `price_min` и `price_max` отсутствуют и в Android-интерфейсе API.

Следовательно, на дату документа:

- география полностью работает при создании объявления;
- backend готов фильтровать по субъекту и району;
- пользователь Android не может применить этот фильтр в каталоге.

Для полноценного фильтра нужны UI выбора региона/района, хранение выбранных ID в `FeedViewModel`, передача их в repository/API и явная кнопка сброса.

## 8. Работа с субъектами РФ

Список субъектов загружается через `GET /geo/regions`. Регион обязателен при публикации. После выбора:

1. сбрасываются старые район и населенный пункт;
2. загружаются районы выбранного субъекта;
3. после выбора района загружаются населенные пункты;
4. район и населенный пункт остаются необязательными.

Каждый список открывается в диалоге с локальным поиском по названию. Backend при отсутствии данных запрашивает их у DaData и кэширует в PostgreSQL. Это снижает повторную нагрузку, но первый запрос для нового региона/района зависит от доступности и лимитов DaData.

Термин «регион» в коде соответствует субъекту РФ. В карточке выводится цепочка «субъект, район, населенный пункт».

## 9. Как работает админка

Админка — отдельное Vue-приложение с пятью разделами. JWT хранится в `localStorage.admin_token`, добавляется как Bearer-токен к API-запросам. При ответе 401 токен удаляется и браузер переходит на вход.

### 9.1. Вход

Администратор вводит email и пароль. Используется общий endpoint `/auth/login`. Клиентская маршрутизация проверяет наличие токена, но реальная защита должна выполняться backend-проверкой `is_admin` на каждом admin-endpoint.

### 9.2. Дашборд

Показывает:

- общее число объявлений;
- число пользователей;
- количество объявлений на модерации;
- общий доход;
- до пяти ближайших объявлений на модерации;
- до пяти новых запросов на контакты.

OpenAPI дополнительно возвращает активные объявления, ожидающие запросы и доход текущего месяца, но текущий экран показывает не все эти показатели.

### 9.3. Модерация

Каждое ожидающее объявление выводится отдельной карточкой с полной информацией и галереей. Доступны публикация, возврат на исправление и отклонение. Для двух негативных решений комментарий обязателен; фото опциональны, максимум пять.

После решения карточка удаляется из очереди. Счетчик очереди в боковом меню обновляется каждые 30 секунд.

### 9.4. Заявки на контакты

Администратор видит объявление, соискателя, его телефон и дату запроса. Возможны действия:

- «Одобрить бесплатно» — контакты сразу выдаются обеим сторонам;
- «Назначить цену» — от 1 до 50 000 ₽, шаг интерфейса 100 ₽, значение по умолчанию 500 ₽, комментарий необязателен;
- «Отклонить».

После назначения цены сервер должен уведомить соискателя. В Android нет экрана со списком заявок и кнопки оплаты, поэтому платный сценарий сейчас не завершен end-to-end.

### 9.5. Все объявления

Таблица показывает фото, название, тип, цену, статус, буст, регион и дату публикации. Есть пагинация по 20 элементов, поиск, выбор типа и видимый выбор статуса. Администратор может мягко удалить объявление.

Обнаружен дефект: состояние фильтра статуса меняется в UI, но при запросе `/admin/ads` параметр `status` не добавляется. Поэтому фильтр по статусу визуально существует, но фактически не работает. Фильтры типа и поиска передаются.

### 9.6. Пользователи

Таблица показывает email, ФИО, телефон, статус, роль и дату регистрации. Поиск работает по email или ФИО. Обычного пользователя можно заблокировать и разблокировать. Кнопка блокировки администратора отключена.

### 9.7. Навигация и счетчики

Боковое меню:

- Дашборд;
- Модерация;
- Заявки на контакты;
- Все объявления;
- Пользователи.

У разделов модерации и контактов есть счетчики ожидающих элементов, обновляемые каждые 30 секунд.

## 10. Оплаты и продвижение

Backend содержит endpoints для:

- оплаты размещения;
- оплаты продвижения;
- оплаты контактов;
- webhook ЮKassa.

Уровни продвижения: без продвижения, ТОП на 7 дней и ТОП на 30 дней. Лента сортирует продвигаемые объявления выше, Android визуально выделяет их.

Текущие ограничения:

- размещение отправляется на модерацию временным endpoint без оплаты;
- в Android нет выбора тарифа и перехода на ЮKassa;
- в Android нет оплаты контактов;
- нет пользовательского экрана истории платежей;
- корректность идемпотентности webhook нельзя подтвердить без исходников backend.

## 11. Безопасность

### 11.1. Что реализовано хорошо в Android

1. **Только HTTPS.** `usesCleartextTraffic=false`; базовый API использует HTTPS.
2. **Bearer JWT.** Токен автоматически добавляется ко всем запросам, кроме `/auth/`.
3. **Шифрование токенов.** Access- и refresh-токены хранятся в DataStore только в виде AES-256-GCM шифротекста; ключ находится в Android Keystore.
4. **Автоматическое обновление сессии.** Параллельные 401 синхронизированы; повторные циклы ограничены; при невалидном refresh выполняется logout.
5. **Резервное копирование отключено.** `allowBackup=false`; DataStore дополнительно исключен из cloud backup и device-to-device transfer.
6. **Логи сети отключены в release.** BODY-логирование включается только в debug.
7. **FCM-сервис не экспортируется.** `android:exported=false`.
8. **Звонок без опасного разрешения.** Используется номеронабиратель, а не прямой вызов.
9. **Клиентская валидация.** Проверяются обязательные поля, число фото, длина названия и наличие телефона/региона.
10. **Release-обфускация.** Для release включены minify и shrink resources; DTO защищены правилами ProGuard/R8.

### 11.2. Критический риск: серверный ключ Firebase в клиентской папке

В рабочем каталоге присутствует незатреканный JSON service account Firebase: `app/agromarket-7bdd5-firebase-adminsdk-fbsvc-5da392f6cb.json`. Это серверные учетные данные с приватным ключом. Такой файл нельзя хранить в Android-проекте, включать в APK, отправлять в git или передавать третьим лицам.

Нужно немедленно:

1. проверить, не попадал ли файл в архивы, APK, облака, чаты или историю git;
2. отозвать/удалить соответствующий ключ в Google Cloud IAM и создать новый для backend;
3. хранить новый ключ только на сервере в secret storage или защищенной переменной/смонтированном файле;
4. добавить в `.gitignore` шаблоны service-account JSON и `app/google-services.json`;
5. добавить secret scanning в CI.

`google-services.json` — клиентская конфигурация Firebase, а не service account, но ее также следует контролировать и ограничить Firebase/Google API keys по package name и SHA-сертификатам.

### 11.3. Риски Android-клиента

- Debug-сборка логирует тела запросов и ответов. В лог могут попасть email, пароль, телефоны и другие персональные данные. Debug APK нельзя использовать как production-релиз.
- Certificate pinning не реализован. HTTPS защищает канал, но приложение доверяет системному хранилищу сертификатов.
- Приложение запрашивает CAMERA и доступ к изображениям, хотя основной выбор идет через Photo Picker; объем разрешений нужно сверить с требованиями Google Play.
- Нет пользовательского удаления аккаунта и явного управления сроком хранения персональных данных.
- Черновик объявления хранит телефон и географию локально без отдельного шифрования. Токены зашифрованы, данные черновика — нет.

### 11.4. Риски админки

- Admin JWT хранится в localStorage. При XSS злоумышленник может его прочитать. Более безопасный вариант — короткоживущий access-токен в памяти и refresh-сессия в `HttpOnly; Secure; SameSite` cookie.
- Клиентский route guard проверяет только наличие токена. Безопасность зависит от обязательной серверной проверки `is_admin` на каждом endpoint; исходники backend в локальном репозитории отсутствуют, поэтому это не подтверждено аудитом.
- Двухфакторная аутентификация администратора не реализована.
- Не обнаружены подтверждения CSP, rate limiting входа, защиты от перебора паролей, журналирования действий администратора и ограничения сессий.
- Кнопка удаления любого объявления требует только UI-подтверждение; сервер должен проверять роль и вести аудит операции.

### 11.5. Персональные данные и бизнес-логика контактов

Проект обрабатывает email, ФИО, телефоны, регион/район/населенный пункт, фотографии, push-токены и платежные сведения. Нужны политика конфиденциальности, пользовательское согласие, сроки хранения, процедура удаления и ограничение доступа сотрудников.

Главная текущая проблема — номер продавца виден в карточке до решения по заявке на контакты. Если бизнес-модель предполагает платную выдачу контактов, API ленты/деталей не должен возвращать телефон неавторизованному на его получение пользователю. Сервер должен выдавать маску и раскрывать номер только владельцу, администратору или после статуса `completed`.

### 11.6. Backend и инфраструктура: что подтверждено

- API использует Bearer-аутентификацию.
- Регистрация подтверждает email кодом.
- Смена пароля требует текущий пароль.
- Объявления имеют владельца и отдельные admin-endpoints.
- Удаление объявления описано как мягкое.
- Подключение к Supabase переведено на Transaction Pooler; ранее превышение лимита соединений вызывало массовые 500, после исправления был выполнен параллельный тест.
- Backend, Celery worker и Celery beat развернуты отдельно.

### 11.7. Backend и инфраструктура: что нельзя подтвердить

Без серверных исходников и конфигурации нельзя утверждать наличие или корректность:

- хэширования паролей современным алгоритмом;
- проверки срока и одноразовости email-кодов;
- rate limiting и защиты от brute force;
- проверки `is_admin` на всех административных endpoints;
- объектной авторизации: может ли пользователь менять/удалять чужое объявление;
- серверной проверки MIME, размера и содержимого изображений;
- антивирусной обработки файлов;
- защиты платежного webhook и его идемпотентности;
- шифрования резервных копий;
- ротации и хранения секретов;
- централизованного аудита действий;
- мониторинга, алертов и плана восстановления.

### 11.8. Риск управления исходниками

Проектные записи указывают, что backend и admin-panel на VPS не находятся под git и сам VPS считается источником правды. Это высокий операционный риск:

- изменения трудно воспроизводить и проверять;
- откат зависит от ручных файлов `.bak`;
- сервер может разойтись с Android-контрактом;
- сложнее проводить security review и восстановление после инцидента.

Backend и admin-panel необходимо перенести в закрытый git-репозиторий, отделить конфигурацию от кода, внедрить CI/CD и хранить секреты вне репозитория.

## 12. Приоритетные доработки

### P0 — немедленно

1. Отозвать обнаруженный Firebase service account key и удалить файл из клиентской папки.
2. Расширить `.gitignore`, включить secret scanning и проверить историю/архивы.
3. Убедиться, что debug APK не используется как production-релиз.

### P1 — до запуска монетизации

1. Скрыть телефоны до разрешенного получения контактов.
2. Завершить Android-сценарии оплаты размещения, буста и контактов.
3. Проверить идемпотентность и подпись webhook ЮKassa.
4. Добавить server-side rate limiting, admin 2FA и аудит действий.
5. Перенести backend/admin-panel под git и CI/CD.

### P2 — обязательная функциональность каталога

1. Добавить фильтр по субъекту РФ и району.
2. Добавить диапазон цены.
3. Исправить фильтр статуса в «Все объявления» админки.
4. Добавить отдельную обработку `pending_payment`, `expired`, `deleted`, `needs_revision` во всех UI.
5. Добавить экран «Мои запросы на контакты» и их статусы.

### P3 — качество и развитие

1. Добавить историю модерации, а не только последний непогашенный комментарий.
2. Добавить управление вторым телефоном в Android.
3. Добавить изменение региона профиля.
4. Добавить наблюдаемость, SLO и проверяемый disaster recovery plan.
5. Провести отдельный backend security audit после получения исходников.

## 13. Итоговая оценка готовности

Основной бесплатный цикл работает целостно: регистрация → каталог → создание объявления → фото → модерация → публикация или доработка → повторная отправка. Android-клиент содержит продуманную работу с токенами, черновиками, ошибками, фотографиями и статусами.

Админка закрывает ежедневные операции модератора и управления пользователями. При этом монетизация пока частичная: backend-контракт существует, но мобильные платежные сценарии не завершены, а открытый телефон противоречит платной выдаче контактов.

Фильтрация по субъектам РФ подготовлена на backend и используется при создании объявления, но отсутствует в каталоге Android. Безопасность мобильного хранения JWT реализована хорошо, однако наличие service account key в клиентском каталоге и отсутствие версионирования backend/admin-panel требуют немедленного исправления.
